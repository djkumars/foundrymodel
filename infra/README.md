# Development infrastructure

This is a **not-yet-deployed** Bicep design for the existing chatbot. It targets
East US 2 by default; no subscription, identity tenant, model quota, or live
deployment was available for validation.

## Architecture

```text
Browser -> Front Door Standard + custom WAF -> Storage static website (Angular)
                                            -> App Service (only this Front Door)
                                                   |
                                          VNet-integrated subnet
                                          /        |          \
                                    Foundry    Content Safety  Cosmos DB
                                                   \
                                                 Key Vault
```

- Storage serves public static files; Front Door provides the CDN and routes
  `/api/*` to the API without caching. `/chat` is rewritten to `index.html`.
  Blob versioning and seven-day soft deletion protect website content from
  accidental removal; retained versions consume storage.
- [Front Door does not support server-sent events](https://learn.microsoft.com/azure/frontdoor/standard-premium/websocket).
  Configure `useStreaming: false` in the deployed frontend so it uses the
  authenticated JSON endpoint. Replies and token usage appear when complete;
  incremental streaming remains available locally with `useStreaming: true`.
- A Linux B1 App Service has HTTPS/TLS 1.2, disabled FTP/SCM basic auth,
  Front Door service-tag plus profile-ID restrictions, and a separately
  IP-restricted SCM deployment endpoint.
- An integration subnet uses service endpoints and service-side VNet rules for
  Cosmos DB, Foundry, Content Safety, and Key Vault. These use public service
  endpoints, **not private endpoints**. Outbound internet traffic is not
  restricted to a fixed allowlist. The VNet is for outbound integration; it
  does not make the App Service inbound endpoint private.
- Cosmos DB serverless uses the `/ownerId` partition key and a new container.
  Existing anonymous history is not migrated. Foundry has a project, a
  `gpt-4o` model deployment, and the platform's default content filtering.
  Content Safety supplies the API's fail-closed Prompt Shields screening.
  The system instructions remain in the API's
  [`ChatPromptTemplate.cs`](../foundry-chatbot-api/Prompts/ChatPromptTemplate.cs);
  a model deployment does not store or enforce them independently.
- API keys are generated by Azure and written directly into Key Vault; the app
  retrieves them through its user-assigned managed identity. This is compatible
  with the current API, which still requires keys for Foundry, Prompt Shields,
  and Cosmos. Local/key authentication is therefore **not disabled** for
  those services. Key rotation must also update the corresponding vault secret;
  versionless references can take time to refresh.
- Front Door/WAF logs are sent to a 30-day Log Analytics workspace; an
  Application Insights resource is provisioned. The API does not currently
  install an Application Insights SDK, so application traces are not guaranteed
  without further instrumentation.

### Security and cost boundaries

This is a development baseline, **not a guarantee of complete security** or a
production-ready security assessment:

- Standard Front Door WAF supports the configured custom rate-limit rule, **not
  managed OWASP rules or Private Link origins**. The static website origin is
  publicly reachable directly and bypasses Front Door/WAF. Never publish
  secrets or private data in it. Upgrade to Premium with managed WAF and
  private origins if origin isolation is required.
- Service-endpoint rules restrict the data services to the integration subnet,
  but the endpoints remain public and administrators outside that subnet
  cannot use data-plane tools without an approved network access path. Key
  Vault firewall rules apply to its data plane; Azure Resource Manager control
  plane operations require separate RBAC protection.
- Access logs can contain URLs, including conversation search terms; review
  logging, retention, privacy, and access controls before using real data.
- The default NSG does not implement outbound deny-by-default; no centralized
  egress firewall, DDoS Network Protection, customer-managed encryption
  keys, security alerts, backup restore testing, zone redundancy, or disaster
  recovery is included. Azure manages the underlying physical infrastructure;
  this template cannot configure its hardware security.
- This creates billable resources including a continuously running B1 plan,
  Front Door/WAF, Cosmos, Foundry, Content Safety, storage and logs. Review
  pricing and set a budget/alerts before deployment. Model inference and
  Prompt Shields are usage-based.

## Prerequisites

1. Azure CLI 2.48.1 or later, Bicep, .NET 10 SDK, Node.js, npm, and `zip`.
   Sign in to the correct subscription. Creating resource groups/resources
   and Key Vault role assignments requires appropriate Azure RBAC permissions;
   tenant creation and Graph registration require separate permissions.
2. Register the necessary providers in the subscription and check regional
   availability and quota for `gpt-4o`, model version and SKU, Content Safety,
   App Service, and Cosmos. The `2024-11-20` GPT-4o version is classified as
   legacy; check the current [retirement schedule](https://learn.microsoft.com/azure/foundry/openai/concepts/model-retirement-schedule)
   and subscription-specific availability. Deployment has **no automatic
   model upgrade**; evaluate and explicitly change the version before expiry.
3. Follow [identity setup](identity/README.md). Create the External ID tenant
   and API/SPA app registrations first, with `http://localhost:4200/auth-callback.html`
   as an initial SPA redirect. Record the tenant GUID, tenant label, API
   client GUID, and SPA client GUID. User flow, consent, and Front Door
   callback registration require explicit follow-up.
4. Choose the public IPv4 CIDR of the trusted machine/runner that will deploy
   the API (for example `203.0.113.10/32`, replace with the real address).
   SCM remains inaccessible outside that CIDR. Deploy using Entra
   authentication; publishing basic auth is disabled.

## Provision in two stages

Run from the repository root. Replace the placeholders; these identifiers are
not secrets. Set the subscription explicitly. Review a `what-if` before each
deployment. Do not execute these commands until cost and access are approved.

```sh
az account set --subscription '<subscription-id>'
az group create --name '<resource-group>' --location eastus2

az deployment group what-if --resource-group '<resource-group>' \
  --template-file infra/main.bicep \
  --parameters externalTenantId='<tenant-guid>' externalTenantName='<tenant-label>' \
    externalApiClientId='<api-client-guid>' deploymentIpCidr='<deployment-ip>/32'

az deployment group create --name chatbot-infra --resource-group '<resource-group>' \
  --template-file infra/main.bicep \
  --parameters externalTenantId='<tenant-guid>' externalTenantName='<tenant-label>' \
    externalApiClientId='<api-client-guid>' deploymentIpCidr='<deployment-ip>/32'
```

In the first stage `webOriginHostName` is empty: the core resources are created,
but no Front Door endpoint/routes are created yet. Obtain `storageAccountName`
and `apiAppName` from the deployment outputs. Storage static website hosting is
a data-plane setting, so enable it with an identity that has
**Storage Account Contributor** and **Storage Blob Data Contributor** on the
account. Role propagation may take several minutes.

```sh
az storage blob service-properties update --account-name '<storage-account>' \
  --auth-mode login --static-website --index-document index.html --404-document index.html
az storage account show --resource-group '<resource-group>' --name '<storage-account>' \
  --query primaryEndpoints.web --output tsv
```

Use the resulting website **hostname only**, without `https://` or the trailing
slash, for stage two. Repeat the same values for all other parameters:

```sh
az deployment group what-if --resource-group '<resource-group>' \
  --template-file infra/main.bicep \
  --parameters externalTenantId='<tenant-guid>' externalTenantName='<tenant-label>' \
    externalApiClientId='<api-client-guid>' deploymentIpCidr='<deployment-ip>/32' \
    webOriginHostName='<storage-static-website-hostname>'

az deployment group create --name chatbot-infra --resource-group '<resource-group>' \
  --template-file infra/main.bicep \
  --parameters externalTenantId='<tenant-guid>' externalTenantName='<tenant-label>' \
    externalApiClientId='<api-client-guid>' deploymentIpCidr='<deployment-ip>/32' \
    webOriginHostName='<storage-static-website-hostname>'
```

Record `frontDoorHostName` from the outputs and register
`https://<frontDoorHostName>/auth-callback.html` as an SPA redirect URI. Add
the SPA to the sign-up/sign-in user flow and grant consent as required. The
separate External ID tenant's data residency is **not** determined by `eastus2`.

## Deploy application artifacts

Build the Angular app, then replace the generated `auth-config.json` in its
`dist/chatbot-plugin/browser` output with the public identifiers from the
identity setup guide and set `useStreaming` to `false`. Never put keys or tokens
in that file. Upload the entire
build output to `$web` with Entra authentication; set `Cache-Control: no-store`
on `auth-config.json` and `index.html` so deployment changes are not cached.

```json
{
  "clientId": "YOUR-SPA-APPLICATION-GUID",
  "authority": "https://YOUR-TENANT.ciamlogin.com/YOUR-TENANT-GUID",
  "apiScope": "api://YOUR-API-APPLICATION-GUID/access_as_user",
  "useStreaming": false
}
```

```sh
cd chatbot-plugin
npm ci
npm run build
# Edit dist/chatbot-plugin/browser/auth-config.json before uploading:
# clientId: SPA GUID; authority: https://<tenant-label>.ciamlogin.com/<tenant-guid>
# apiScope: api://<api-client-guid>/access_as_user; useStreaming: false
az storage blob upload-batch --account-name '<storage-account>' --auth-mode login \
  --destination '$web' --source dist/chatbot-plugin/browser --overwrite
az storage blob upload --account-name '<storage-account>' --auth-mode login \
  --container-name '$web' --name auth-config.json \
  --file dist/chatbot-plugin/browser/auth-config.json --content-cache-control no-store --overwrite
az storage blob upload --account-name '<storage-account>' --auth-mode login \
  --container-name '$web' --name index.html \
  --file dist/chatbot-plugin/browser/index.html --content-cache-control no-store --overwrite
cd ..
```

Publish the API into a fresh temporary directory, zip the **contents** of that
directory, and use `az webapp deploy --resource-group <resource-group> --name
<apiAppName> --src-path <zip-file> --type zip` from the allowed SCM address.
Use Azure CLI 2.48.1+ so deployment can use Entra authentication when basic
auth is disabled. See [App Service deployment authentication](https://learn.microsoft.com/azure/app-service/configure-basic-auth-disable#deploy-without-basic-authentication).
The infrastructure does not upload application code automatically.

## Validation before use

1. From the Front Door URL check `/chat`, the MSAL callback assets, and
   `/api/health`; an anonymous chat/search request must return 401.
2. Confirm direct App Service requests are denied, SCM rejects other source
   IPs, data services reject traffic outside the approved subnet, and Key
   Vault references resolve. Wait for RBAC, network, and Front Door propagation.
3. Test sign-up/sign-in, token claims, non-streaming replies, Prompt Shields, and two
   distinct users' search/history isolation across devices. Test WAF rate
   limiting, older history pages and deployed CDN cache behavior.
4. Test failure and recovery, backup restoration, monitoring, cost alerts,
   token/key rotation, and the intended browsers' popup/storage restrictions.
   The deployed services and identity flow have not been integration-tested.
